# Parity harness (old Server vs. the new NestJS server)

Purpose: prove that the rewritten server answers like the old one. It starts both servers against the **same disposable test
database**, sends the same requests to both and compares the responses. No recorded responses are stored in git, because the test
database contains customer and order rows.

Zero dependencies, plain Node 24. Run everything from the repository root.

## Safety rules (built in)
- `safe-env.js` sets every environment variable the servers read, so `Server/.env` (live database, live Mollie key, real mail account)
  is never loaded. Mollie and mail use dummy values: payment and mail calls fail harmlessly.
- The database must be local and its name must end in `_test`, otherwise `start-server.js` and `--include-mutations` refuse to run.
- The runner only sends GET requests unless `--include-mutations` is given **and** `PARITY_CONFIRM_DISPOSABLE_DB=yes` is set.
- Differences are printed and saved as JSON paths and types only, never values. `parity/reports/` is git-ignored anyway.

## The test database
`docker-compose.yml` defines `cooplubbers_mysql` (MySQL 8, database `cooplubbers_test`, seeded from `Database/Dump20240103 (3).sql`).
On this project it runs under Podman (`podman compose up -d`); Docker works the same. The dump only contains the shop database
(`cooplubbers_test`); the store site database (`shops`, used by `/api/v2`) is not in it, so `/api/v2` endpoints answer 400 on the old
server for now. `reseed.ps1` drops and reloads `cooplubbers_test` from the dump (needed after mutating runs).

## Usage
The short way for a module: `node parity/check.js --spec auth,reference-data` builds ServerNest, loads the fixtures, starts both servers, runs the specs, stops the servers and removes the fixtures (see the header of `check.js`). The individual commands:

```
node parity/list-endpoints.js --write      # regenerate parity/inventory.json from the old Server's routers
node --test parity/tests/*.test.js          # unit tests of the comparator

node parity/start-server.js --dir Server --port 3101                      # old server (restarts itself when it crashes)
node parity/start-server.js --dir ServerNest --port 3102 --cmd "npm run start"   # new server (later)

node parity/run.js --old http://127.0.0.1:3101 --new http://127.0.0.1:3102
node parity/run.js --old http://127.0.0.1:3101 --new http://127.0.0.1:3101      # self-check: is the old server deterministic?
```
`run.js` prints `same` / `DIFF` per endpoint with both status codes and exits with 1 when anything differs. `timeout` means the
endpoint never answered, `error` means the connection failed (the old server crashed on that request).

## Files
| File | What |
|---|---|
| `inventory.json` | every endpoint of the old server (method, path, `usedByKlant`), generated by `list-endpoints.js` |
| `list-endpoints.js` | records the Express router calls while the route files load; matches them with the calls in `Klant/src` |
| `compare.js` | response comparison (status, content type, normalised JSON, volatile fields like timestamps and tokens ignored) |
| `run.js` | sends the requests to both servers and reports |
| `start-server.js` | starts a server with the safe environment and restarts it when it exits |
| `safe-env.js` | the safe environment and the "disposable database" check |
| `reseed.ps1` | reloads the test database from the dump (PowerShell, Podman or Docker) |

## Fixtures and specs
`fixtures/*.sql` create test accounts in the disposable database (`fixtures/load.ps1 auth.sql`, remove with `auth-cleanup.sql`; run PowerShell with `-ExecutionPolicy Bypass` if scripts are blocked). `specs/*.json` are request lists for `run.js --spec`; requests that change data need `--include-mutations`. Example: `specs/auth.json` compares all login cases.

## Extending it per module
Each NestJS module revision adds requests for its endpoints to a spec file (`--spec parity/specs/<module>.json`, array of
`{ name, method, path, headers?, body?, mutation? }`), including authenticated calls and calls with path parameters, and only then is
the module considered done. Known, accepted differences are listed in that module's revision document.
